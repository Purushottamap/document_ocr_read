# Document status retry Lambda

This is a standalone Java 21 Lambda project. Configure it as an SQS event source consumer for the queue used by the upload Lambda. The SQS message body is the Sarvam OCR job ID (the unique key). For each invocation, the worker checks the Sarvam job status. When status is `completed` (or `success`), it requests the job results and stops retrying. For any other status, it sends a new message containing the same `documentId`, incremented `retryCount`, and ISO-8601 `nextRetryAt`.

The SQS event is decoded by `SqsMessageReader`; `DocumentStatusRetryHandler` coordinates retries; `SarvamAiClient` owns HTTP calls. The worker calls `SARVAM_OCR_BASE_URL` plus `SARVAM_OCR_STATUS_PATH` and `SARVAM_OCR_RESULTS_PATH`, substituting the URL-encoded job ID for `%s`. Requests use the `api-subscription-key` header when `SARVAM_OCR_API_KEY` is configured. Status is read from `DOCUMENT_STATUS_FIELD` (default `status`). HTTP or parsing errors fail the Lambda invocation so the SQS event source's normal retry and DLQ policy applies.

Pending jobs are polled again after `SARVAM_OCR_POLL_INTERVAL_MS` (default 2000 ms). SQS message delays use whole seconds, so this interval is rounded up for the queue delay. SQS supports at most 900 seconds of per-message delay; longer intervals stay in `nextRetryAt` and are rescheduled in 900-second increments until due.

Configure the Lambda under **Configuration → Environment variables** with `SQS_QUEUE_URL`, `SARVAM_OCR_BASE_URL`, `SARVAM_OCR_API_KEY`, `SARVAM_OCR_STATUS_PATH`, `SARVAM_OCR_RESULTS_PATH`, and `SARVAM_OCR_POLL_INTERVAL_MS`. Optional variables are `SARVAM_OCR_SUCCESS_STATUS`, `DOCUMENT_STATUS_FIELD`, and `API_TIMEOUT_SECONDS`. Environment variables take precedence over properties in a file. A properties file is only read as a fallback; when the default file is absent, the Lambda starts with environment variables alone. Set `APP_CONFIG_FILE` only when using a custom fallback file path.

`SARVAM_OCR_SCHEMA` is used by the OCR job creation flow; this retry worker only consumes the resulting job ID and does not submit OCR jobs. `SARVAM_OCR_MAX_WAIT_SECONDS` is available to that calling workflow; retry state is persisted in SQS messages. Build with `mvn package` from this directory. Configure the Lambda handler as `com.affordplan.documentstatus.DocumentStatusRetryHandler::handleRequest`. Its role needs `sqs:ReceiveMessage`, `sqs:DeleteMessage`, `sqs:GetQueueAttributes`, and `sqs:SendMessage` on the queue, plus CloudWatch Logs permissions. Give the SQS event source mapping a visibility timeout longer than the Lambda timeout and configure a DLQ/redrive policy for invocation errors.
